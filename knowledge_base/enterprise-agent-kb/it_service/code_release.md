# 代码发布流程

## 一、流程总览

公司所有代码变更（功能开发、Bug修复、配置变更）必须通过标准发布流程才能上线。

```
开发完成 → 代码Review → 测试环境部署 → QA测试 → 预发布验证 → 生产发布 → 线上验证
```

## 二、各阶段详细说明

### 2.1 代码Review

#### 提交要求
- 创建 Merge Request（MR），填写以下信息：
  - **变更描述**：本次变更做了什么
  - **关联需求/Bug**：关联 JIRA/TAPD 单号
  - **影响范围**：涉及哪些模块/服务
  - **自测情况**：自测用例和结果
  - **回滚方案**：如出问题如何回滚

#### Review规则
| MR类型 | 最少Review人数 | 必须Reviewer |
|--------|--------------|-------------|
| 功能开发 | 2人 | 技术Lead + 1名同组工程师 |
| Bug修复 | 1人 | 技术Lead或指定工程师 |
| 配置变更 | 2人 | 技术Lead + SRE |
| 数据库变更 | 2人 | DBA + 技术Lead |
| 安全相关 | 3人 | 安全工程师 + 技术Lead + VP |

#### Review重点
- 代码逻辑正确性
- 是否有安全隐患
- 性能影响评估
- 测试覆盖率（要求≥80%）
- 是否遵循编码规范

### 2.2 测试环境部署

#### 部署方式
- 开发分支合并到 `develop` 分支后自动部署到测试环境
- 部署时间：合并后15分钟内自动完成
- 测试环境地址：`test-xxx.company.internal`

#### 部署后自检
- 服务是否正常启动（健康检查接口）
- 数据库迁移是否成功
- 配置是否正确加载
- 关联服务是否正常调用

### 2.3 QA测试

#### 测试类型
| 测试类型 | 负责人 | 时间要求 | 通过标准 |
|---------|--------|---------|---------|
| 功能测试 | QA工程师 | 1-3个工作日 | 全部用例通过 |
| 回归测试 | QA工程师 | 0.5-1个工作日 | 无新增缺陷 |
| 性能测试 | SRE+QA | 按需 | 满足性能指标 |
| 安全测试 | 安全工程师 | 按需 | 无高危漏洞 |

#### 缺陷管理
| 缺陷等级 | 修复时限 | 发布影响 |
|---------|---------|---------|
| P0-阻塞 | 当天 | 阻断发布 |
| P1-严重 | 1个工作日 | 阻断发布 |
| P2-一般 | 当前迭代内 | 不阻断但需修复 |
| P3-轻微 | 下个迭代 | 不阻断 |

### 2.4 预发布验证

#### 预发布环境
- 与生产环境配置一致（除数据库为只读镜像）
- 地址：`staging-xxx.company.internal`
- 部署方式：从 `release` 分支部署

#### 验证内容
- 产品经理验收功能
- 开发确认技术实现
- SRE确认监控和告警配置
- 确认回滚方案可执行

### 2.5 生产发布

#### 发布窗口
| 发布类型 | 允许时间 | 审批要求 |
|---------|---------|---------|
| 常规发布 | 周二/周四 14:00-17:00 | 技术Lead审批 |
| 紧急修复 | 任意工作日 10:00-20:00 | 技术经理审批 |
| 重大版本 | 需提前3天申请 | 技术总监审批 |
| 禁止发布 | 周五下午、节假日前一天 | — |

#### 发布流程
1. 发布申请：在OA填写发布单，关联MR和测试报告
2. 审批确认：技术Lead确认发布条件
3. 灰度发布：先发布10%流量，观察15分钟
4. 全量发布：灰度无异常后全量切换
5. 线上验证：开发和QA执行冒烟测试用例

#### 发布检查清单
- [ ] 所有测试用例通过
- [ ] 数据库迁移脚本已验证
- [ ] 回滚方案已准备
- [ ] 监控告警已配置
- [ ] 相关方已通知
- [ ] 文档已更新

### 2.6 线上验证

#### 发布后观察
- **15分钟内**：关注错误日志、接口响应时间、错误率
- **1小时内**：关注业务指标是否正常
- **24小时内**：关注是否有延迟暴露的问题

#### 异常处理
| 情况 | 处理方式 |
|------|---------|
| 错误率>1% | 立即回滚 |
| 核心接口RT>3s | 回滚或降级 |
| 数据异常 | 立即回滚 |
| 非核心功能异常 | 评估影响，决定是否回滚 |

## 三、紧急发布（Hotfix）

### 适用场景
- 线上P0故障需要立即修复
- 安全漏洞需要紧急修补
- 数据异常需要紧急修正

### 流程简化
```
Hotfix分支 → 快速Review（1人即可） → 快速测试（核心用例） → 技术经理口头审批 → 发布
```

### 后续要求
- 发布后24小时内补齐测试用例
- 48小时内补齐文档
- 事故后3天内完成复盘报告

## 四、版本管理

### 分支策略
| 分支 | 用途 | 生命周期 |
|------|------|---------|
| main | 生产代码 | 永久 |
| develop | 开发集成分支 | 永久 |
| feature/* | 功能开发 | 功能发布后删除 |
| hotfix/* | 紧急修复 | 修复发布后删除 |
| release/* | 发布准备 | 发布完成后删除 |

### 版本号规范
- 格式：`v主版本.次版本.修订号`（如 v2.3.1）
- 主版本：不兼容的大变更
- 次版本：向下兼容的功能新增
- 修订号：向下兼容的Bug修复

## 常见问题FAQ

### Q1: 我的MR被拒了怎么办？
**A**: 查看Review意见，修改后重新提交。如有分歧，可拉技术Lead仲裁。

### Q2: 发布当天有问题但已经过了发布窗口怎么办？
**A**: 非紧急情况等到下一个发布窗口。紧急情况走Hotfix流程。

### Q3: 测试环境没问题，上线后出问题了怎么办？
**A**: 立即回滚，然后在测试环境复现问题。检查测试环境与生产环境的配置差异。

### Q4: 可以直接往main分支提交代码吗？
**A**: 不可以。所有代码必须通过MR经过Review后合并，禁止直接push到main。
